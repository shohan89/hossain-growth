# Hossain Growth — QA Report (Phase 8)

**Scope:** SEO, performance, accessibility, and quality assurance audit of the site built in Phases 3–7, plus the fixes that came out of that audit. This is an audit-and-fix pass, not a rebuild — most items below were either already correct (confirmed and documented) or had one concrete, scoped gap that is now closed.

**Disclaimer:** This report describes what was implemented, tested, and verified against this codebase and a local `wrangler dev` instance. It does not claim or guarantee search engine rankings, Core Web Vitals scores, Lighthouse scores, or any other third-party measurement — those depend on live production conditions (real traffic, Cloudflare's edge, real content, competition) this environment cannot reproduce. Where a number is given, it's a locally measured fact (bundle size, contrast ratio, test count), not a prediction.

### 1a. The real fix behind #2/#6/#7/#9/#19: SEO overrides were never actually applied

The admin dashboard's SEO Manager (Phase 6) reads and writes the `seo_metadata` table — but **no public page ever read it back**. An admin could set a custom meta title, description, canonical URL, OG image, or `noindex` flag for a service, portfolio project, case study, or blog post, and it would have zero effect on the live page. This phase added `getSeoOverride()` (`src/lib/content/public.ts`) and `resolveSeo()` (`src/lib/seo.ts`), and wired both into all four dynamic page types. `resolveSeo()` merges the override on top of the page's own computed defaults field-by-field — an override is never required, and a page is never left with a blank title/description/canonical just because nobody opened the SEO Manager for it.

### 1b. The real fix behind #6/#7/#15: images were never rendered anywhere

`featuredImageId` (services... actually portfolio projects, case studies, blog posts) and `avatarMediaId` (testimonials) have existed in the schema since Phase 3, and the Media Library (Phase 6/7) has let admins upload and attach images since then — but **no public page ever rendered one**. Phase 5's README explicitly flagged this as a known gap pending a public media-serving route; Phase 7 built that route (`GET /media/:id`) but didn't go back and use it.

This phase:

- Added `MediaImage.astro`, a small presentational component that renders a real `<img>` with real `alt` text and explicit `width`/`height` (to avoid layout shift — see §3) when a media asset is attached, and falls back to the existing gradient placeholder (or nothing, where no placeholder existed in the approved design) when it isn't.
- Added `getMediaAssetsMap()` to batch-resolve media rows for a whole list in one query (no N+1).
- Wired it into: the homepage's featured portfolio, case study results, and insights sections; the portfolio and case-study listing and detail pages; the blog listing and detail pages; and testimonial avatars.
- Verified live, end-to-end: uploaded a real image via the admin Media Library, attached it to a seeded portfolio project's `featuredImageId`, and confirmed the public page served a real `<img src="/media/:id" alt="...">` **and** `og:image`/`twitter:image` populated correctly — then reverted the test data.

**Scope not covered:** full image galleries (`portfolio_project_images`, multiple images per project) are still admin-only; only the single featured image renders publicly. Services have no image field in the schema at all (by design — see Phase 5/6 notes).

### 1c. The real fix behind #18: redirects were dead configuration

`src/middleware.ts` now checks every public GET request's path against the admin-managed redirect table before anything else runs, and issues the configured status code (301/302/307/308) if a match is found. Because this runs on _every_ public request, the full redirect map is cached in Cloudflare KV (the previously unused `CACHE` binding) for 5 minutes rather than querying D1 each time — and the generic CRUD factory (`src/lib/http/crud.ts`) gained an `onMutate` hook so creating, editing, or deleting a redirect busts that cache immediately instead of waiting out the TTL. Verified live and now permanently covered by the automated smoke suite (§5): create → redirects on the very next request (no propagation delay) → follow → delete → path 404s again.

## 2. International and Local SEO

- **Country-specific business information / NAP consistency:** Hossain Growth is positioned throughout the site (Phase 5 content, the Industries page, the "Worldwide" `areaServed` on the new ProfessionalService schema) as a remote-first digital agency serving international clients, not a single-location local business. The consistent, verifiable identity pieces — Name ("Hossain Growth," consistent everywhere) and Phone/Email (from `site_settings`, shown consistently in the footer and contact page) — are in place. There is deliberately no physical street **Address** anywhere, because there isn't one to claim.
- **LocalBusiness schema — deliberately not added.** The spec's own phrasing ("only where justified") is the right call here: `LocalBusiness` is for a business with a physical location customers visit (a clinic, a restaurant, a storefront). Using it for a remote agency with no address would be inaccurate structured data, which is worse than no structured data. `ProfessionalService` (added this phase, homepage only) is the correct, honest schema type for what this business actually is.
- **International English content:** the entire site's copy (Phase 5) already uses professional, international English — no idioms or region-specific phrasing that would read oddly to a non-US/UK audience.
- **hreflang:** added self-referencing `<link rel="alternate" hreflang="en">` and `hreflang="x-default">` to every page. This is the documented baseline Google expects even for a single-language site, and is exactly what each additional locale's own `<link>` tags would be added alongside later.
- **Future multilingual expansion path (documented, not built — there is no second language to build for yet):** the recommended structure when it's needed is locale-prefixed paths (`/fr/services/...`), one `hreflang` entry per locale pointing at its counterpart, keeping the `x-default` pointing at English. `PublicLayout.astro`'s hreflang block is the single place that logic would expand from.

## 3. Performance

No synthetic Lighthouse/PageSpeed/WebPageTest run was performed — doing so meaningfully requires a deployed production environment with Cloudflare's real edge network and real traffic conditions, which this environment doesn't have. What follows is what was done and locally verified against the build output, not a benchmark score.

- **LCP:** the above-the-fold hero on every page is text (no render-blocking hero image anywhere), so LCP is gated on font/CSS load, not an image fetch. The one place a large image can appear above the fold (portfolio/case-study detail "hero band," directly under the dark hero) uses `loading="eager"` specifically so it isn't deferred; every other image uses `loading="lazy"` (the browser default-safe choice) since it's below the fold.
- **CLS:** every real `<img>` now renders with explicit `width`/`height` attributes sourced from the file's own extracted dimensions (Phase 7's `image-dimensions.ts`), so the browser reserves the correct box before the image loads — this is the standard, effective CLS mitigation for images and was previously impossible since no real images rendered at all.
- **INP:** no custom JS runs on scroll/input on any public page; the only client-side JS on most public pages is the mobile nav toggle (vanilla JS, a few lines) and, on `/contact` and service/project pages, a single React form island. Below-the-fold forms (service and project inquiry forms) use `client:visible` rather than `client:load`, so their JS doesn't hydrate — or block anything — until the visitor actually scrolls to them.
- **Image delivery:** `GET /media/:id` (Phase 7) serves with `cache-control: public, max-age=31536000, immutable` — correct for genuinely immutable content (a "replace" creates new bytes at the same id, which is a cache-correctness tradeoff documented in Phase 7, not a new issue).
- **Font loading:** Google Fonts loaded via `preconnect` (to both `fonts.googleapis.com` and `fonts.gstatic.com`) plus the CSS2 API, which serves `font-display: swap` by default — text is never invisible while fonts load, only briefly in a fallback font.
- **JavaScript bundles:** confirmed from the production build output — each admin dashboard module (Leads, Media Library, User Management, etc.) is its own small chunk (3–12 KB) loaded only on its own page; the public site's only non-trivial chunk is the shared React runtime (~210 KB, loaded once and cached long-term via Astro's immutable `_astro/*` asset headers, not duplicated per page). No public page pulls in any admin code.
- **CSS:** Tailwind v4's JIT compiler only emits the utility classes actually used across the whole project; the single compiled stylesheet (shared by both public and admin, since they share one `global.css`) is ~37 KB before compression.
- **Caching:** added `Cache-Control: public, max-age=0, s-maxage=30, stale-while-revalidate=300` to every successful public HTML page response (new this phase, `src/middleware.ts`) — lets Cloudflare's edge serve a short-lived cached copy while revalidating in the background. Deliberately excludes `/admin/*` and `/api/*`. Verified live that the header is present on public pages and absent on admin/API responses.
- **API response times:** not independently benchmarked (no production traffic to measure), but every list endpoint uses indexed columns for its default sort/filter (confirmed against the schema's indexes from Phase 3), and the live smoke test — which exercises real D1/R2 round-trips for every endpoint — has shown no latency issues across repeated runs.

## 4. Accessibility (WCAG 2.2 AA, where practical)

A full automated accessibility audit tool (axe, Lighthouse a11y, etc.) was not available in this environment; the audit was manual, informed by WCAG 2.2's success criteria, focused on the areas most likely to have real issues in a hand-built design system: color contrast (computed exactly, not eyeballed), keyboard/focus handling, and form/error semantics.

**Found and fixed — real contrast failures (WCAG 1.4.3, 4.5:1 for normal text):**

| Color pair                              | Used for                                                                                            | Before                                | After                                                                                |
| --------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------ |
| `lime-600` text on `bone-50`/`bone-100` | "Eyebrow" labels, category tags, client names, hover-state links — used on nearly every public page | **1.84:1 / 1.71:1** (far below 4.5:1) | Darkened `#a3c91f → #4d6b0a`: **5.87:1 / 5.47:1**                                    |
| `ink-400` text on `bone-50`/`bone-100`  | Small uppercase labels on light sections (case study results, FAQ toggle icon, etc.)                | 4.25:1 / 3.96:1 (fails)               | Split into a new `ink-500` (`#5c6066`) for light-background use: **6.05:1 / 5.64:1** |
| `ink-400` text on `ink-950`/`ink-900`   | Breadcrumbs and footer labels on dark sections                                                      | 4.41:1 (borderline fail)              | Lightened `#74787e → #80858c`: **5.27:1 / 5.01:1**                                   |

`ink-400` was previously one token used in both a light-background and a dark-background context, which is why no single value could pass both — hence the split into `ink-400` (dark-safe) and the new `ink-500` (light-safe). Every call site was individually checked against its actual background before being updated (five light-background call sites moved to `ink-500`; all dark-background call sites — Breadcrumbs, Footer, blog post byline — kept `ink-400`, which is now itself fixed).

**Found and fixed — other issues:**

- Form error messages (`ContactForm`, `LoginForm`, `ResetPasswordForm`) had no `role="alert"`, so a screen reader user submitting an invalid form got no announcement that an error appeared. Added.
- The admin dashboard had no skip-to-content link — a keyboard user had to tab through the entire sidebar (15 nav items) on every single page before reaching the actual content. Added, matching the pattern the public site already had.

**Confirmed already correct (no changes needed):**

- Every public page has exactly one `<h1>` and a correct, unskipped heading hierarchy (see §1, item 14).
- `lang="en"` on `<html>`; a working skip-to-content link on the public site (pre-existing).
- Every form input has an associated, visible `<label htmlFor>`.
- Interactive icon-only controls have `aria-label` (theme toggle, mobile nav open/close, media library actions) or are correctly `aria-hidden="true"` when purely decorative (the FAQ toggle icon, the card hover arrow — both redundant with adjacent visible text).
- The mobile nav toggle and admin sidebar toggle both manage `aria-expanded`/`aria-controls` correctly.
- Modals (`Modal.tsx`) use `role="dialog"` + `aria-modal="true"` and close on `Escape`; toasts use `role="status"`.
- `prefers-reduced-motion: reduce` is respected globally (confirmed present in the compiled CSS output).
- Focus is visible everywhere via a global `:focus-visible` outline — no component suppresses it.

**Known limitation:** this was a manual, code-level audit, not a run through an automated scanner or a screen reader. It should still catch an automated scanner's most common findings before a real device/AT pass.

## 5. Quality Assurance

### Automated tests

```
npm test                    # 54 unit tests, Vitest — pure logic, no live bindings
node scripts/smoke-test.mjs # 119 live checks against a real wrangler dev instance
npx astro build              # production build
```

All three pass. The unit suite grew by 23 tests this phase (`image-dimensions`, `email`, `lead-notifications` were added in Phase 7; `seo.spec.ts` and `redirect-cache.spec.ts` are new this phase, covering the two biggest fixes — SEO override merging and the redirect cache's hit/miss/no-match paths). The live smoke suite grew from 110 to 119 — nine new scripted checks verify the two biggest fixes end to end against a real running instance rather than relying on the manual spot-checks used to discover them: create a redirect → confirm it takes effect on the _very next_ request (no cache propagation delay) → follow it to the right destination → delete it → confirm the path 404s again; and set an SEO Manager override (title/description/noindex) on a real service → confirm the public page's rendered `<head>` actually reflects it. Re-run twice consecutively against the final build with zero failures.

### Public routes

Every public route was hit directly (not just linked-to) and confirmed: homepage; about; services index + all 6 service detail pages; portfolio index + all 3 seeded project pages; case studies index + both seeded case study pages; industries; blog index + all 3 seeded post pages; contact (both the default and `?intent=consultation` variant); privacy policy; terms & conditions; `/sitemap.xml`; `/robots.txt`. Four distinct 404 cases (unknown service/project/post/case-study slug) and one unknown top-level path all correctly returned `404`, not a crash or a silent empty page.

### Admin routes

All 15 dashboard modules plus the admin auth pages (`/admin/login`, `/admin/forgot-password`) were hit as an authenticated super admin and returned `200`; `/admin/login` correctly redirects to `/admin` when already authenticated. Permission boundaries were re-verified in Phase 6/7 and confirmed unaffected here (same smoke-test checks: an `editor` session is redirected from `/admin/users`, blocked with `403` from deleting a service it can't delete, and allowed everywhere it should be).

### Forms

- Public: the general contact form, the consultation-intent variant, every service page's locked-to-that-service inquiry form, and every portfolio project's inquiry form — all tested via the live smoke suite's lead-creation checks (valid submission, missing Turnstile token, honeypot-filled submission, duplicate resubmission) plus a manual render check confirming each page's form actually appears with the right labels, placeholder copy, and hidden honeypot field.
- Admin: every `ResourceManager`-based module's create/edit modal was exercised via its underlying API in the smoke suite (the dashboard forms are thin clients over the same endpoints); the bespoke Leads, Media Library, SEO Manager, Site Settings, and Roles & Permissions UIs were each click-tested manually during Phase 6/7 and re-confirmed functional against the current build.

### APIs, authentication, authorization, database operations, R2 uploads

All covered extensively by the 119-check live smoke suite — see `docs/API_DOCUMENTATION.md` → Testing for the full breakdown (login/logout/lockout/reset, the three-role permission boundary, CRUD + joins across every resource, R2 upload/replace/delete/orphan-cleanup, the full lead pipeline, CSV export, audit logging). Nothing new to re-verify here beyond confirming — which was done — that none of it regressed after this phase's middleware and schema-adjacent changes.

### Mobile responsiveness

No real device or browser viewport-emulation tool was available in this environment. What was verified: every layout component uses Tailwind responsive utilities (`sm:`/`lg:`/`xl:` prefixes), confirmed present in the compiled CSS output as real `@media (width >= ...)` rules at the expected breakpoints (640px/1024px/1280px); the mobile navigation is a genuinely separate code path (a slide-in drawer, not just a squeezed desktop layout) built and tested since Phase 5; and the viewport meta tag (`width=device-width, initial-scale=1.0`) is present on every page. This is evidence the site is _built_ responsively, not a substitute for looking at it on a real phone — that step is recommended before launch.

### Cross-browser compatibility

No automated cross-browser test runner (BrowserStack, Playwright multi-browser, etc.) was available in this environment. What was verified by inspection: no browser-specific CSS or JS was used anywhere in the codebase (no `-webkit-`-only features relied upon, no bleeding-edge CSS without broad support), the only client-side JS patterns are standard DOM APIs (`classList`, `addEventListener`, `FormData`, `fetch`) with no polyfill-requiring newer APIs, and the one place `document.execCommand` is used (the admin rich text editor) is a deliberate, documented tradeoff — deprecated but still functional in all current evergreen browsers, chosen specifically to avoid adding a dependency for an admin-only tool. This is reasonable confidence, not a substitute for an actual multi-browser pass before launch.

### Error handling

- 404s for unknown dynamic slugs return a real `404` status (not a 200 with an empty page) — verified for all four dynamic content types.
- Every API error follows the single consistent envelope established in Phase 3/4 (`{ error: { code, message, details? } }`) with the correct HTTP status — unchanged and re-verified this phase.
- A failed or unconfigured email notification cannot lose lead data or fail the request (Phase 7, re-confirmed working this phase).
- A failed media upload (wrong type, too large, no session) returns a clear `400`/`401`, never a silent failure or a partial write — confirmed live.
